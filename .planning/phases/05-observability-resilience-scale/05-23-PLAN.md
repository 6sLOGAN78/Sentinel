<interfaces>
`func (s *QueryEventStore) SummarizeEvents(ctx, tenant string, now time.Time) (query.EventSummary, error)`. It returns RateCount (winners with occurred_at >= now-1m) and Trend (5-minute buckets from end-24h to end, where end = now truncated to SummaryBucketWidth; buckets before end only). Winner occurred_at is the argMin by the canonical tuple from `uniqueEventRowsSQL`.

Key fact for the fast path: when every row of an event_id has the same occurred_at, the winner's occurred_at equals that value no matter how ties are broken. Only identities whose rows disagree on occurred_at (conflicting payloads, allowed but unspecified by ADR 0002) need the full canonical tie-break.
</interfaces>

  <action>Rewrite the SummarizeEvents SQL as an exact decomposition. The proof goes in the doc comment, replacing "selects the complete canonical identity before applying any occurrence-time predicate".

1. Main query (round trip 1, query_id `<prefix>` or `<prefix>-main`): one `GROUP BY event_id` over `events WHERE tenant_id={tenant}` computing lo=min(occurred_at) and hi=max(occurred_at), reading only tenant_id, event_id and occurred_at. It returns two things in one result: the per-bucket counts and the rate count for identities with lo == hi and lo in [start, now) (the winner's occurred_at is lo regardless of tie-break), and the list of conflicting event_ids (lo != hi). It never references a payload column. Use e.g. `WITH ids AS (...)` with a UNION ALL of the bucket rows and the conflicting-id rows distinguished by a kind column, or two result columns, whichever keeps the scan single.
2. Correction query (round trip 2, query_id suffix `-correction`): runs ONLY when the conflicting set is non-empty. It applies the existing canonical argMin over `events WHERE tenant_id={tenant} AND event_id IN {ids:Array(String)}` (bound parameter), and returns each winner's occurred_at. Go buckets these winners into the same buckets and rate window.
3. Go sums both parts. The conflicting set is bounded by client misuse (ADR 0002). Cap it with a named maximum (for example, 10,000 ids). Exceeding the cap returns a wrapped error on the existing 503 path, never a partial summary.
4. Snapshot semantics, documented in the doc comment and in ADR 0002: the result reflects the main query's read point. Rows inserted between the two round trips may be missing. This is benign because ClickHouse events are append-only, and the correction only refines identities the main query already counted as conflicting; it never adds identities.
