## Phase Goal

**As an** operator, **I want to** see pipeline health and have failure and scale behavior proven by tests and a reproducible benchmark report, **so that** reliability and performance are demonstrated rather than claimed.

<objective>
Build the benchmark workload model as a runnable, tested library. It provides a live-time, bounded-entity, open-loop schedule with injected attacks and an exact expected-hit plan, plus the capacity and benign-threshold preflight that makes "expected benign hits = 0" and "detector stays under caps" checked facts.

Purpose: BENCH-01 needs a configurable benign+malicious open-loop scenario. BENCH-02 needs exactly known expected rule hits. RESEARCH Pitfalls 1-2 show the existing generator cannot do 1M events (it starts 11.6 days in the past and draws IPs uniformly). The existing `generate_events`/`build_event`/`send` stay untouched because seed contracts depend on them.
Output: `sentinel_generator.bench` package (model, schedule, preflight) and pytest coverage.

Default bench design (assumptions recorded in SUMMARY; the user may override via config):
- N=3 detectors and 6 partitions.
- Target 400 ev/s and batch size 200, so 1M events take about 2,500 s.
- Bounded pools: source_pool 200, a fixed principal per source for benign auth.failure, destination_pool 2, port_pool 16, attacks_per_rule 30 (120 expected alerts, which is ≥ 100, so SSE p99 is reportable).
- These defaults were recomputed from the real detector window key in revision 2. The arithmetic and margins are below under "Capacity arithmetic for the defaults". The round-1 defaults (source_pool 2,000, principal_pool 500 drawn independently, destination_pool 64, auth.failure 5%) predicted about 24,800 windows per process, which is 3.1× the 8,000 budget, so they were wrong. They are kept as a must-fail test fixture.
- The benign mix includes auth.failure at 1% (exact proportions below). RESEARCH Open Question 4 is resolved by the default "realistic mix". A `benign_auth_failure=false` config switch exists for a clearly labelled second scenario, and the preflight decides whether capacity allows the default.

**Detector window key (read from source, not assumed).** `backend/internal/detection/reducer.go` prepareWindow builds `windowKey{tenant, rule, ip: source IP, principal: second, start}`, where `second` comes from `ruleGroup`:
- AUTH_BRUTE_FORCE: auth.failure with a principal; second = principal
- PORT_SCAN: net.connection with source, destination IP and port; second = destination IP, and ports are counted per window
- REQUEST_FLOOD: net.request; second = ""
- DENY_SPIKE: policy.decision with action=deny; second = ""

Windows are bucket-aligned. A window is deleted once its end ≤ the sealed watermark (max − 30 s), so a key can hold a current bucket and a previous one for up to `window + 30 s`.

The kafka record key is tenant|source_ip. Each surviving process therefore owns about f_proc of the sources.

Byte charges (reducer.go:25-28, bounds.go windowBytes):
- ledgerEntryBytes 64
- eventEntryBytes 128 + len(event_id)
- windowBaseBytes 1024 + key string lengths
- portEntryBytes 32 per distinct port

**Capacity arithmetic for the defaults.** Inputs: R=400 ev/s, N=3, P=6, share_max=1/6 (so f_proc = ceil(6/2)×1/6 = 0.5 and R_proc = 200 ev/s), L=30 s.

Per-process benign rates from the mix:

| type | share | ev/s |
|---|---|---|
| net.connection | 40% | 80 |
| net.request | 30% | 60 |
| policy.decision deny | 15% × 20% | 6 |
| auth.failure | 1% | 2 |

Per-process key spaces: AUTH K = 200 (source, fixed principal) pairs × 0.5 = 100; SCAN K = 200 × 2 destinations × 0.5 = 200; FLOOD K = 100; DENY K = 100.

Windows: windows_r = 2 × min(K_r,proc, E_r), where E_r is the rule-matching events in (W_r + L).

| rule | E_r | min(K, E) | windows |
|---|---|---|---|
| AUTH | 2 × 330 = 660 | 100 | 200 |
| SCAN | 80 × 90 = 7,200 | 200 | 400 |
| FLOOD | 60 × 90 = 5,400 | 100 | 200 |
| DENY | 6 × 150 = 900 | 100 | 200 |

Benign windows total 1,000. Attack term: 4 rules × 30 entities × 2 = 240, a worst-case bound assuming every attack window is simultaneously open. Predicted 1,240 of the 8,000 budget (15.5%; 12.4% of the 10,000 cap).

Ledger: R_proc × H = 200 × 330 = 66,000, below the 80,000 budget (66% of the 100,000 cap; 14,000 entries of headroom, which tolerates a partition-share skew up to 1/6 × 80/66 ≈ 0.202).

Bytes, about 7.8 MB in total, below the 53.7 MB budget (12% of 64 MiB):
- ledger: 66,000 × 64 = 4.22 MB
- retained event IDs: (660 + 7,200 + 5,400 + 900) × (128 + 36) = 2.32 MB
- windows: 1,240 × (1024 + ~64 key bytes) = 1.35 MB
- SCAN ports: 400 × 16 × 32 = 0.20 MB

Benign threshold safety, per key per bucket. Deterministic round-robin quotas make the maximum exact:
- AUTH: auth.failure 4 ev/s global ÷ 200 pairs × 300 s = 6, below the threshold of 10
- SCAN: distinct ports ≤ port_pool 16, below 20 (impossible to reach)
- FLOOD: 120 ev/s ÷ 200 sources × 60 s = 36, below 300
- DENY: 12 ev/s ÷ 200 × 120 s = 7.2, so a maximum of 8 with integer rounding, below 30

benign_threshold_check still computes the exact maxima over the generated stream and fails if any reaches its threshold.

If the measured warm-up skew makes any prediction exceed 80%, the preflight refuses. The documented remedy is a lower `--rate` (ledger scales linearly) or smaller pools, never a looser formula.
</objective>
