**Sequencing:** edits Phase 4-owned `App.tsx` and `Overview.tsx`. Must not start before Phase 4 closes (04-16 accepted). The executor verifies this first.

UI-SPEC checker recommendations adopted (binding for this plan):
1. **Rename the ingest result label "Unavailable" to "Dependency unavailable"** in the result breakdown, so it is never confused with the "Unavailable" availability badge.
2. **Headline ↔ badge mapping:**
   - "All services ready" → success "Ready" badge.
   - "{n} of {m} services not ready" → critical "Not ready" badge if any service is not_ready, else warning "Degraded" badge.
   - "Service health unavailable" → muted "Unavailable" badge.
3. **Degraded counting:** n counts every service whose readiness state ≠ ready (degraded + not_ready + unavailable), and m = 5.
4. **Staleness is measured from the client's last successful fetch time** (React Query `dataUpdatedAt`), not server `observed_at`, so clock skew cannot fake staleness. The "Updated" text still shows server observed_at.
5. **The header (h2 + description) stays rendered during loading.** Only the content area shows "Loading system status…" (no toolbar values, no zeros).

Output: client method, System page + tests, nav/route, Overview lag panel + tests, one CSS grid rule. The human visual/responsive/keyboard check against live data happens in 05-20, while the isolated bench stack is running, so no fixture or mock data code is shipped for a demo.
</objective>
