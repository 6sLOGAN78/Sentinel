## Phase Goal

**As an** operator, **I want to** see pipeline health and have failure and scale behavior proven by tests and a reproducible benchmark report, **so that** reliability and performance are demonstrated rather than claimed.

<objective>
Second tracing slice: carry the trace through the workers. The detector extracts the record header and starts `detect` for sampled parents, then injects into the alert record. The event-writer opens one `store` span per CH batch with links to at most 32 sampled record contexts. The alert-writer extracts the alert header for `store_alert`. All three binaries are wired with telemetry.Tracing and shutdown ordering. One integration test proves the full chain.

Purpose: completes OBS-04 (ingestion, publishing, detection, storage spans through Kafka headers). It also gives OBS-03 trace_id on worker logs.
Output: worker spans, alert header injection, binary wiring, and the end-to-end propagation test.

Span attributes are limited to rule_id, partition, offset and batch size. No tenant/IP/principal attributes.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-12-01 | Denial of service | span explosion at bench rates | mitigate | Spans only for sampled parents (ParentBased). One store span per batch with ≤ 32 links. Bounded BSP queue |
| T-05-12-02 | Information disclosure | entity data in spans | mitigate | Attribute allowlist (rule_id, partition, offset, batch.size). grep guard in acceptance |
| T-05-12-03 | Tampering | header manipulation alters processing | mitigate | Trace context is observability-only. Detection/commit logic never reads it. Regression families rerun |
| T-05-12-04 | Repudiation | spans lost on shutdown | mitigate | The tracing closer runs after the workers stop (LIFO registration), and Shutdown flushes |
</threat_model>
