  <name>Task 1: Choose the detector expired-history recovery design (G7)</name>
  <decision>How should an operator recover a detector whose committed checkpoints fell below the Kafka log start after an idle period, without silently skipping data and without violating the PG fence/epoch rules? Should the plan also prevent the related 7-day group-offset expiry?</decision>
  <context>
Facts:
- (1) Records in [processed_next, log_start) expired before the detector evaluated them. They cannot be recovered from Kafka. The event-writer may have stored them in ClickHouse, but detection on them is lost. Any recovery must therefore record an acknowledged loss.
- (2) PG fences must not be rewritten or reset. Deleting the Kafka group resets the generation, and the fences then reject it.
- (3) Keeping the SAME group keeps its generation as long as the group still exists (it has committed offsets).
- (4) The existing detector already fails closed, so nothing is skipped today. The problem is that there is no sanctioned way forward except renaming the group, which discards cooldown and decision lineage continuity and grows config drift.

The user directive: automatic silent recovery is NOT acceptable. An operator-acknowledged, audited path is required.

Option A details:
- Dry-run prints a JSON plan (group, topic, partition, committed, log_start, log_end, never_evaluated_from/to, open_windows_discarded, plan_digest).
- Apply requires --acknowledge-loss=&lt;plan_digest&gt; --operator=&lt;name&gt; --reason=&lt;text&gt;, recomputes the plan and refuses on any digest change, and verifies zero group members immediately before the commit.
- It inserts PG audit rows in a new append-only table detection_history_recoveries (migration 009) with status pending. It then commits the re-pinned checkpoints to the same group with the Kafka admin OffsetCommit (generation -1, which keeps the group), verifies them with FetchOffsets, and marks the rows applied.
- It never writes detection_partition_fences.
- The detector then restores through its normal path, unchanged.
  </context>
  <options>
    <option id="option-a">
      <name>A (RECOMMENDED): Offline operator tool, same group, digest-acknowledged, audited re-pin</name>
      <pros>No change to the hot restore path, so the detector stays fail-closed by default. Same group, so generation, fences, cooldown cursors and decision lineage are preserved. The two-step dry-run/apply with a digest makes the acknowledgment explicit and specific to the incident. TOCTOU is guarded by recomputation and a zero-member check. There is a durable PG audit plus a structured log line. It is idempotent: a rerun with nothing lost is a no-op. Exposed as make detector-recover-history (dry-run by default) and documented in operations.md and ADR 0012.</pros>
      <cons>It is a new tool, a new migration and a new runbook step. The operator must stop detectors first. The open window state of an undrained checkpoint is discarded, but this is reported in the plan and audit.</cons>
    </option>
