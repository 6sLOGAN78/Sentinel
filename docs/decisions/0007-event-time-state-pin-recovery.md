# 0007. Event-time state pins and replay recovery

## Status

Accepted engineering policy, 2026-10-17. Implements spec §5.1 and inherited D-15/D-16. The user's cross-window cooldown choice in `03-COOLDOWN-DECISION.md` supersedes candidate-only throttling. This record specifies the final Phase 3 contract; the first AUTH slice precedes the durable cooldown implementation and is not proof of that final contract.

## Decision

All instants are UTC milliseconds. Windows are epoch-aligned tumbling `[start,end)` intervals. The partition watermark is the maximum valid occurred_at minus 30 seconds. Equality is accepted; older events are dropped. Every valid nonmatching event advances the maximum; poison records and idle wall time do not. Null grouping fields mean no match. Require the existing canonical `tenant|source_ip` input key.

Freeze the first threshold crossing: accepted unique event count, first at most 20 event IDs in partition order, deterministic summary, status=open, created_at=window_end and no detected_at. Existing `contracts.DedupeKey` is the only alert-ID encoder; rule version is excluded. Retain fired identities and dedupe state until event-time expiry.

Startup YAML is one strict document, capped at 64 KiB, with four known rule IDs and positive bounded settings. Defaults (all version 1) are AUTH: 10/300s, high/60s cooldown; SCAN: 20 distinct ports/60s, medium/30s; FLOOD: 300/60s, high/30s; DENY: 30/120s, medium/60s. AUTH groups source IP/principal; SCAN source/destination IP; FLOOD and DENY source IP, always within tenant. Startup changes require restart and a verified drained handover; unchanged active replay requires the same fingerprint and four-rule version manifest. For a changed window, persist effective_from=ceil(max verified handover sealed floor/new window)*new window, so enlarged windows cannot reinterpret historical identities.

Commit a resume pin at the earliest first offset of every unexpired state, including fired states. With no state, commit processed-next. Maintain a bounded offset/prefix-maximum ledger: metadata's prefix maximum is the maximum immediately BEFORE the pin, never the current maximum. Publication and every poison/decision effect must be acknowledged before adopting a new sealed floor, retiring windows or committing. Replay starts at pin with its prefix maximum, suppressing windows whose end is at/before the saved durable sealed floor.

Atomically commit offset plus format-2 metadata (at most 1024 bytes): config_fingerprint, all four rule_versions, nullable prefix_max_event_time and sealed_through (null means empty prefix), processed_next independent of pin, all four rule_effective_from gates, drained, and decision_frontier. The latter is explicit none or source offset/rule ordinal/alert ID/immutable fingerprint. Metadata is restored through OnOffsetsFetched and attached by PreCommitFnContext. Check CommitOffsetsSync transport, every partition result and response completeness. Terminal restore failures must reach the process lifecycle, not retry indefinitely while ready. New groups start at retained earliest; existing groups use NoResetOffset and fail closed on missing/corrupt metadata, pin loss, truncation or ownership loss.

Bounds are admission limits, not benchmark claims: 10,000 active windows, 4096 unique IDs/window, 100,000 prefix-ledger entries, 64 MiB tracked state/process, 1s..1h windows, thresholds 1..4096 (SCAN up to 65536 subject to exact-set limits), finite fetch/producer queues and an aggregate owned-batch deadline. No eviction of unexpired state. Capacity exhaustion marks not-ready and terminates without advancing unsafe checkpoints. Retention must cover the oldest pin plus downtime; idle partitions retain state indefinitely until event time advances.

## Cross-window cooldown and durable operational state

Cooldown applies per rule/tenant/injective entity components across windows. Freeze trigger occurred_at and source position internally, without changing Alert. For a new candidate, clock=max(cursor.max_candidate_time, trigger occurred_at). Suppress if clock<next_eligible_at; allow equality. Allow advances eligibility by cooldown; suppression does not. Neither time field rewinds.

PostgreSQL operational rows are separate from analyst workflow: immutable detection_decisions (allow/suppress, canonical bytes/fingerprint, source position, original config/version and trigger/clock); unique detection_cooldown_cursors per entity/config generation; and detection_partition_fences per stable group incarnation/topic/partition with Kafka generation/member, assignment token, config, greatest decided offset/rule ordinal and drained handover. Lock fence first, validate ownership/config, then look up immutable decision. Matching replay returns its original decision and bytes before consulting today's cursor. Different reconstructed bytes fail closed. A missing decision at/before the fence frontier fails closed. Otherwise lock/create cursor, decide, insert immutable decision and advance cursor/fence in one bounded transaction. Roll back explicitly on failure; hold no PG transaction during Kafka publish.

Allow ordering is PG decision commit → canonical Kafka publish → all-ISR acknowledgement → Kafka pin/metadata commit. Suppress ordering is PG decision commit → no publication → checkpoint. PG may be ahead after decision-before-publish crashes. Restore verifies the checkpoint frontier's exact immutable row and PG fence >= marker; missing, older or divergent PG state fails closed. Do not require PG equality. Group recreation/generation rollback requires explicit stopped maintenance, never automatic adoption. Revoke/loss prevents new decisions/commits; stale assignment cannot supersede newer generation/member ownership. No automatic decision GC is permitted: disk growth, Kafka retention and consistent PG/Kafka backups are operational obligations.

## Live scenarios and consequences

Private operator tooling snapshots source ends and group metadata, waits for processed_next catch-up and derives processed maximum from sealed_through+lateness (with explicit empty/idle handling), not pre-pin max. A capped retained-history scan may support this private tool. Under quiescent other producers, base>=max(now, observed maxima+1ms); same-ms threat events precede per-key auth.success markers at window end+30s. Schedule within ingest future-skew limits and a 15-minute orchestration deadline, retaining the sender's five-attempt/120s per-batch budget. Far-future/concurrent traffic causes bounded refusal. No group reset, public debug API or volume reset.

At-least-once Kafka publication can repeat identical bytes after a crash. Immutable identity and downstream idempotency collapse visible duplicates; no distributed transaction or end-to-end exactly-once claim is made. Recovery, handover and cooldown require the later named Phase 3 proofs.
